# 2026-07-13 — Autoregressive models in EDGAR

## Aims
- [x] Agree on what the AR problem actually is (see `2026-07-13_notion_doc.md`)
- [x] Settle the sample/param/rollout contract
- [x] Build a synthetic ground truth that genuinely requires autoregression
- [x] Write `projects/synthetic_data_v2/`
- [ ] Make `evaluate` the single point of model evaluation inside `edgar/`

## Decisions

- **Sample = recording.** Model maps `(n_cells, L) -> (n_cells,)`; params are per-recording.
  Preserves EDGAR's per-sample-params contract. For the eventual long volumetric dataset the
  same shape holds with sample = a contiguous multi-minute *segment*, where per-segment params
  are meaningful (brain-state drift), so nothing in the project code changes.
- **Loss = H-step rollout with teacher-forced restarts, stride 1.** From every start index, feed
  the true window, roll H steps on the model's own predictions, score all H. H=1 is
  one-step-ahead. Default H=3. Stride 1 (not H) so every timepoint is graded at every horizon
  rather than at whichever horizon the block boundaries happen to align it to. Consequence: the
  per-horizon losses are correlated, so the loss is a fine objective but not an unbiased estimate
  with a clean error bar.
- **`evaluate.py` is per-project** and returns `(preds, targets)`. Rationale: the window/target
  alignment must be written exactly once. The notion doc contains two versions of that alignment
  and they disagree (the loop version leaks `x_t` into the window; the vmap version doesn't). I
  then made the same class of off-by-one in a diagnostic plot. It is not a bug you avoid by being
  careful.
- **`loss_fn` stays in `load_data.py`** — revised from the earlier plan to move it. Because
  `evaluate` returns the aligned targets, `loss_fn` does no indexing at all (it is a pure
  comparison), so the one-place-for-alignment argument is already satisfied and moving it would
  be churn for nothing.
- Model never receives the data dict under AR — it gets a window — so the "return the target"
  cheat closes structurally. No general key-filtering mechanism needed.
- `complexity_penalty` stays out of projects: scoring already applies
  `param_penalty_weight * n_params`, and `n_params` counts array *elements*
  (`program.py:339`), so an N×N coupling correctly costs 1024.
- **Project is named `synthetic_data_v2`, not `ring_attractor`** — the name would hand the
  answer to the LLM, which reads the project only through the prompt but shouldn't be given
  free hints anywhere.

## Synthetic benchmark — `2026-07-13_ar_synth.py`

Ring attractor (N=32) with spike-frequency adaptation. We observe only the activity `x`;
the adaptation current `a` is **hidden**:

    x_i(t+1) = A x_i(t) + dt ( sum_j K(i-j) phi(x_j(t)) - g a_i(t) ) + eps
    a_i(t+1) = B a_i(t) + dt x_i(t)

`a` eliminates exactly (one-pole linear filter), giving the observed-form ground truth:

    x(t+1) = (A+B) x(t) - (AB + g dt^2) x(t-1) + dt [ C(t) - B C(t-1) ],  C(t) = K * phi(x(t))

An exact AR(2) **whose second lag is the unobserved adaptation current**. Verified numerically:
max abs error 1.3e-15 at zero noise. Biological grounding: ring attractor + adaptation is the
standard travelling-bump circuit, and adaptation is a real single-neuron mechanism — the hidden
variable is not a device.

### Models (held-out MSE; `2026-07-13_ar_synth.py` writes this table)

| model | role | n_params | H=1 | H=3 | H=10 |
|---|---|---|---|---|---|
| persistence | seed | 0 | 0.0103 | 0.0475 | 0.374 |
| AR(1) leak | seed | 1 | 0.0103 | 0.0473 | 0.369 |
| VAR(1) | baseline | 1024 | 0.0414 | 0.170 | 0.975 |
| VAR(2) | baseline | 2048 | 0.00021 | 0.0017 | 0.0396 |
| ground truth | truth | 6 | 0.00005 | 0.00014 | 0.00054 |

VAR = vector autoregression: an unconstrained matrix of every pairwise coupling, no ring, no
kernel, no nonlinearity. It is the strong dumb model EDGAR must beat, and must beat for the
right reason. Note the seeds are weak *and nearly identical* — the fitted leak is
`decay ≈ 0.995`, so AR(1) collapses onto persistence. Two near-identical parents is thin
material for a crossover-based search. Keeping them as-is for now; if EDGAR stalls, add a third
structurally different seed (local diffusion is the obvious candidate, but it hands over
"cells couple to their ring neighbours", which is half the discovery).

Note also VAR(1) is *worse than doing nothing*: 1024 free parameters, fitted largely on the
transients, give a mildly unstable linear system whose errors compound under rollout. Parameter
count buys nothing without the right structure.

### Two findings that changed the design

**1. The data must be forced off the bump manifold.** With recordings started from a settled
bump, trajectories collapse onto a low-dim manifold, the dynamics look linear there, and
VAR(2) *beats the ground truth* on held-out data. Fix: start each recording from a random field
and keep the transient (`init="random"`, `burn_in=0`). The transient sweeps state space and
exercises the rectification.

**2. Rollout horizon is load-bearing, not a nicety.** Eliminating the hidden `a` turns process
noise into MA(1) (moving-average) noise `eps(t) - B eps(t-1)`; `eps(t-1)` is partially inferable
from the observed lags, so least squares can cancel it and the true equation cannot. The true
model is therefore *not* the one-step-ahead MSE optimum. Truth vs VAR(2):

| process_noise | H=1 | H=3 | H=10 |
|---|---|---|---|
| 0.005 | truth 4× better | truth 12× better | truth 70× better |
| 0.02  | VAR wins 1.2× | tie | truth 2× better |

H>1 is what makes the loss select the correct dynamics instead of a linear surrogate.

Also: parameter identifiability degrades badly with process noise (refitting the true functional
form at noise=0.02 returns `tau_x 1.0→0.22, J_e 20→76` at *lower* loss). So the success criterion
is **recovery of the functional form, not the parameters**. This is realistic for attractor data.

Defaults: N=32 cells, 16 recordings × 250 steps, dt=0.1, process_noise=0.005, obs_noise=0.0.

## `projects/synthetic_data_v2/` — written and checked

Verified by `2026-07-13_check_project.py` (loader shapes, leak-freeness, both seeds, gradient
flow through the rollout scan, image feedback). All pass. Seeds score ≈0.043 train / ≈0.043 test,
consistent with the benchmark table.

- `data_loader/load_data.py` — generates the data (`data_path` unused), plus `loss_fn`.
  Sample = recording; each recording's time axis is cut into `block_len=50` blocks, and blocks
  **alternate** train/test so both splits contain the transient and the steady state (a
  first-60%/last-40% split would put the entire transient in train). Data is
  `x: (n_samples, n_blocks, n_cells, block_len)`.
- `evaluate/evaluate.py` — `evaluate(model_fn, data, params) -> (preds, targets)`. vmaps over
  samples, then blocks, then rollout starts; `lax.scan` for the H steps. Windows never cross a
  block boundary, so the train/test split is leak-free by construction.
  `MAX_LENGTH=2`, `ROLLOUT_STEPS=3` are module constants, *not* config — plumbing config into
  `evaluate` needs a signature change we don't yet need.
- `seed_programs/` — persistence (0 params) and leaky decay (1 param). Both single-lag.
- `image_feedback/plot.py` — left column: data and each program's H-step prediction as heatmaps,
  shared colour scale, with colourbars. Right column: the residual (prediction − data) for three
  example cells, at h=1 (thin solid) and h=3 (thick dashed). The residual traces are far more
  diagnostic than a residual heatmap: both seeds' residuals trace the *negative slope* of the
  activity, the signature of a model lagging a moving pattern, and the h=3 residual is ~3× the
  h=1 residual.
- `prompts.yaml` — tells the LLM it is inside an autoregressive loop, spells out exactly how the
  loss is computed (MSE at t+1/t+2/t+3, averaged over steps, cells and every start), that
  `data['x']` is a window, that the cells have a ring ordering, and that parameters are penalised
  elementwise. Also an `image_analysis_instructions` section explaining how to read the figure.
  Verified end-to-end with `scripts/print_prompts.py synthetic_data_v2`.

Fixed a bug in my first draft of the prompt: it said "a population of {num_parents} recorded
cells", but `num_parents` is the number of parent *models* — it would have told the LLM the
population had 2 cells.

**Unresolved: the image-analysis instructions may give the game away.** Telling the LLM that a
residual shaped like the negative slope means it "needs terms that capture how the activity is
moving" is a broad hint towards the second lag, and telling it that ring-localised residuals mean
it is "missing something about how a cell relates to its neighbours" hints at the coupling. That
is both halves of the discovery. Tension: the instructions genuinely have to explain how to read
an unfamiliar figure. Options are to keep them (fastest path to a working run, weakest scientific
claim), or cut the two interpretive sentences and keep only the mechanical description of the
axes and colours. Not yet decided.

Coupling risk: `ROLLOUT_STEPS = 3` lives in `evaluate.py`, but "three steps" is written out in
prose in `prompts.yaml`. Changing one silently desyncs the other.

Caveat to remember: train and test blocks are adjacent in time on the *same* trajectory, so the
within-sample test loss is a weak generalisation check. The real check is the discover/validate
split over held-out recordings.

## Complexity penalty — `2026-07-13_calibrate_penalty.py`

EDGAR ranks on `score = test_loss + w * n_params`, `n_params` counted elementwise. Fitting each
candidate the way `scoring._optimize` does (per sample, Adam on the train rollout loss):

| model | role | n_par | raw loss | w=1e-2 (default) | w=1e-3 | w=1e-4 | **w=1e-5** | w=1e-6 |
|---|---|---|---|---|---|---|---|---|
| persistence | seed | 0 | 0.0437 | **0.0437** | 0.0437 | 0.0437 | 0.0437 | 0.0437 |
| leaky decay | seed | 1 | 0.0436 | 0.0536 | 0.0446 | 0.0437 | 0.0436 | 0.0436 |
| VAR(1) | baseline | 1024 | 0.0272 | 10.27 | 1.051 | 0.130 | 0.0374 | 0.0282 |
| VAR(2) | baseline | 2048 | 0.0195 | 20.50 | 2.068 | 0.224 | 0.0400 | **0.0215** |
| ground truth | truth | 6 | 0.00014 | 0.0601 | **0.0061** | **0.0007** | **0.0002** | 0.0001 |

**The default `param_penalty_weight: 0.01` would break this project outright.** It scores the
ground truth at 0.060 — *worse than doing nothing* (0.0437) — because 6 parameters cost 0.06 while
the entire loss scale is ~0.04. Evolution would converge on persistence. The penalty is absolute,
not relative to the loss scale, so it has to be set per project; `orientation_tuning` gets away
with 0.01 partly because its `loss_fn` multiplies the MSE by 10.

Set **`param_penalty_weight: 1.0e-5`** in the project config. It gives the ground truth a 186×
margin over the runner-up, and it happens to satisfy the design goal of putting VAR(1) (0.0374)
in the same band as leaky decay (0.0436) — a 1024-parameter model is meaningfully but not fatally
penalised, so the LLM can explore a coupling matrix without being killed for it. At w=1e-6 the
penalty stops biting and VAR(2) becomes the runner-up; at w=1e-4 a 1024-parameter model is dead on
arrival.

Robustness check: these VAR numbers come from Adam with a finite budget, which *understates* what
a VAR can do — pooled least squares reaches 0.0017 for VAR(2), 10× better. Do not rely on the
optimiser being weak (the LLM writes the parameter estimator, and could initialise close to the
least-squares solution). But w=1e-5 is safe against that too: even an oracle-fitted VAR(2) at the
noise floor scores ~0.021 against the truth's 0.0002, a 100× margin. The margin comes from the
2048-parameter penalty, not from the optimiser failing.

## `evaluate` is now the single point of model evaluation in `edgar/` — done

- `edgar/scoring/scoring.py`: added `default_evaluate(model_fn, data, params) -> (predictions,
  data)`, which vmaps the model over samples and hands the data dict back as the target — so every
  existing project's `loss_fn(model_output, data)` is unchanged. The four sites that used to call
  `jax.vmap(model_fn, in_axes=(0,0))` directly (`_optimize`, `_eval_loss`, `_eval_sample_losses`,
  `_eval_fingerprint`) now go through `evaluate_fn`. There is no longer any path that evaluates a
  model without it.
- `edgar/io/task_spec.py`: new `evaluate_fn` field, loaded from `<project>/evaluate/evaluate.py`,
  `None` if absent. `edgar/run.py`: passed to all three `score()` calls.
- The private helpers take `evaluate_fn` as a required argument (no hidden fallback — that is the
  point); only the public `score` / `_score_one_model` default it to `default_evaluate`.
- `edgar/cli.py:117` turned out to be an `init-project` *scaffold template*, not a live call site.

### A bug this shook out: `plot.py` could not import its own project's `evaluate.py`

`load_function_from_source` execs project code in a bare namespace, so `__file__` is undefined and
`image_feedback/plot.py` could not locate its sibling `evaluate/evaluate.py`. The plot function
silently failed to load (warning only) — image feedback would never have rendered. Fixed by binding
the source path as `__file__` when the code came from a file, which `task_spec` now passes for
`load_data`, `loss_fn`, `evaluate` and `plot`. LLM-generated code has no path and is unaffected.
The alternative — duplicating the rollout in `plot.py` — would have put the window/target alignment
in two places, which is the thing this whole design exists to prevent.
