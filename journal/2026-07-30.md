### Persistence posts at m=5 — `config.yaml` scoring comment
discover-test, mean over the 2 discover samples (D 0.005 / 0.01):

| h | nl=0.0 | nl=0.01 | nl=0.1 |
|---|---|---|---|
| 1 | 1.91e-05 | 2.37e-05 | 4.87e-04 |
| 2 | 4.69e-05 | 5.15e-05 | 5.13e-04 |
| 4 | 1.35e-04 | 1.40e-04 | 5.98e-04 |

(h=2 was 4.8e-5 / 5.3e-5 / 5.1e-4 at m=2 — small shift, as expected from 197 → 194 starts.)

**The noise floor is exactly additive, and it eats the dynamic range.** Targets are noisy,
so a model that nailed `u_clean` still scores σ². Measured
`persistence(nl) − persistence(0.0)` at h=1 is 4.65e-06 / 4.68e-04 against
`2σ² = 4.65e-06 / 4.65e-04` — agreement to <1%. Headroom between do-nothing and a perfect
model is therefore **unbounded at nl=0.0, ~10× at nl=0.01, and only ~2.1× at nl=0.1**.

Expect the nl=0.1 arm to discriminate weakly between models: it measures noise robustness,
not equation quality. The informative noise range for equation discovery is 0.0–0.01.

### Two launcher limits that blocked the 9 runs
1. **`evaluate` was not an overridable section**, so `--evaluate.rollout_steps=4` raised
   `Unknown section` before provisioning. Added to `edgar/cli.py` and
   `edgar/cloud/launch_gcp.py:OVERRIDE_SECTIONS`; `config.evaluate` is a plain dict, so the
   `project_params` item-assignment branch now covers both (`dict_sections`).
   Verified the override reaches `evaluate_fn.keywords` **and** `flat_config`, and that a
   bogus key is still rejected by the existing signature check in `task_spec.py`.
2. **The data-upload cache was keyed on the config file**, and `build_overrides` emitted the
   VM-side `io.data_path` *before* user overrides. So 9 runs sharing one config would have
   uploaded only `nl_0.0.npz`, then had the user override win and point the VM at a local
   path that does not exist there — a failed run, or worse, silently wrong data. Now
   `validate_spec` resolves an **effective** `data_path` per run (its own `io.data_path`
   override, else the config's), `flatten_runs` carries it, the cache is keyed on it, and
   `build_overrides` drops the user key since it has already been consumed. `preflight`
   checks the per-run paths.

### Quota: 9 VMs → 3 slabs of 3, on L4 → 2 rounds
Launching all 9 failed on `PREEMPTIBLE_NVIDIA_T4_GPUS exceeded. Limit: 4.0 in region
europe-west2`.

**How the quota is defined:** per-project × per-**region** × per-GPU-model ×
per-provisioning-model, counting *concurrent* GPUs. So `europe-west2-a` + `-b` share one
bucket — zones are not a workaround. Different GPU model *is* a different bucket. Measured
limits (identical across europe-west1/2/4 and us-central1):

| GPU | preemptible | on-demand |
|---|---|---|
| T4 | 4 | 4 |
| **L4** | **8** | 8 |
| A100 | 16 | 1 |
| V100 / P4 / P100 | 1 | 1 |

**Decision: move all 9 runs to `nvidia-l4` on `g2-standard-8`** — which is already
`launch_gcp.py:GCP_DEFAULTS`; the old spec was actively overriding *away* from it to
`n1-standard-4` + T4. 8 concurrent means **2 rounds instead of 3**.

| round | spec | dataset | VMs |
|---|---|---|---|
| 1 | `gcp_launch.burgers_3way_nl0.yaml` | `ic_seed_0_nl_0.0.npz` | 3 |
| 1 | `gcp_launch.burgers_3way_nl001.yaml` | `ic_seed_0_nl_0.01.npz` | 3 |
| 2 | `gcp_launch.burgers_3way_nl01.yaml` | `ic_seed_0_nl_0.1.npz` | 3 |

Round 1 = 6 concurrent, inside the limit of 8. Round 2 waits for the VMs to self-delete via
the `trap`; `--teardown` is only for aborting. Split by **noise level** so each launch stages
exactly one `.npz`; `data_path` moved to `defaults.overrides`, constant within a slab.

**All nine on the same GPU model deliberately.** Mixing T4 and L4 would make wall-clock
incomparable against the SINDy / STENCIL-NET timings and change float nondeterminism between
noise levels.

Quota increase not requested — L4 removes the need. If it ever is: billing is enabled
(account `01F642-3D2F61-6565C3`), console route is IAM → Quotas, filter the metric, pick the
`europe-west2` row. Note **quota ≠ capacity**: spot L4 can still return
`ZONE_RESOURCE_POOL_EXHAUSTED` inside quota, and `europe-west2-a` *is* a real fallback for
capacity (just not for quota).

The split is orthogonal to the two launcher fixes above, which are still load-bearing: the
dataset is still expressed as an `io.data_path` **override**, so without the
drop-after-staging in `build_overrides` every VM would still get a local path that does not
exist there. The split only masks the cache-keyed-on-config half of the bug.

Verified per slab by dry-run: one distinct dataset staged, `--io.data_path=/opt/edgar_data/<basename>`
