To run the equation discovery system (EDGAR), the user needs to specify python functions under the seed_programs directory under their
project. These python functions are then compiled as a python object and compiled. 

In burgers project, I would like to supply some helper python functions so that the LLM, which will give RK4 approximation of the differentials, and
let the LLM call these auxiliary function directly into their novel function. 

For example, we will inform the LLM that these functions are available to them inside the model generatio prompt. 

```python 
import numpy as np 

def dudx_fn(u):
    return (np.roll(u, -2) - 8 * np.roll(u, -1) + 8 * np.roll(u, 1) - np.roll(u, 2)) / 12.0

def d2udx2_fn(u):
    return (-np.roll(u, -2) + 16 * np.roll(u, -1) - 30 * u + 16 * np.roll(u, 1) - np.roll(u, 2)) / 12.0
```

The LLM will then generate some code which might (or might not) call some of these functions 
```python 
import numpy as np 

def model(data, params):
    u0 = data["x"][:, -1]

    dudx = dudf_fn(u0)
    return u0 + params['a'] * dudx
```

In order for this function to be runnable, we need to directly expose the auxiliary code inside the model code item for python object Program. 

```python 
import numpy as np 

def dudx(u):
    return (np.roll(u, -2) - 8 * np.roll(u, -1) + 8 * np.roll(u, 1) - np.roll(u, 2)) / 12.0

def d2udx2(u):
    return (-np.roll(u, -2) + 16 * np.roll(u, -1) - 30 * u + 16 * np.roll(u, 1) - np.roll(u, 2)) / 12.0

import numpy as np 

def model(data, params):
    u0 = data["x"][:, -1]

    dudx = dudf_fn(u0)
    return u0 + params['a'] * dudx
```

What does this achieve? 
1. Improve interpretability - currently, the LLM often suggests a function that includes terms that approximate dudx, but as it changes its 
approximation method, it isn't always what approximation it is trying to make.
2. Secondly, this will remove failure modes where the LLM uses a poor approximation method.

## Done

### Auxiliary helper functions — implemented, generic mechanism + burgers helpers

Design differs from the initial plan in one place: helpers are **not** pasted into `code.model`.
They live in their own `Code` fields and are concatenated only at exec time, so the prompts and the
JAX-translation input stay free of helper boilerplate.

| piece | where |
|---|---|
| helper source (np + jnp) | `projects/burgers/seed_programs/auxiliary.py`, `auxiliary_jax.py` — 4th-order central `dudx_fn(u, axis=-1)`, `d2udx2_fn(u, axis=-1)`; neither name matches the seed globs |
| discovery + record | `TaskSpec.from_config` reads both files; `TaskSpec.{auxiliary_code,auxiliary_code_jax}`; written into `task_spec.yaml` |
| prompt exposure | `TaskSpec.flat_config` gains `{auxiliary_code}` / `{auxiliary_code_jax}` — single source of truth, prompt text cannot drift from injected code. Mirrored in `dashboard/data.py:86` and `scripts/print_prompts.py` |
| carried per program | `Code.auxiliary` / `Code.auxiliary_jax`; set for seeds in `from_config`, for children in `_generate_one_model` / `_translate_one_model` |
| exec | `compile_model` = `model_jax + auxiliary_jax`; `compile_param_est` = `param_est + auxiliary` (via `_join_source`) |
| prompts | burgers `model.code_guidelines`, `parameter_estimator.code_guidelines`, and a new `jax_translator_model.base` |

`translate_programs` / `_translate_one_model` now take `config`, so the JAX prompt gets config vars
at generation time (it already did in the *log*, `logging.py:344` — the two were out of step).

**The numpy model code is never executed by the pipeline.** `compile_model` loads `model_jax`; the
only exec of numpy model source is `_extract_default_params` on seed files, which needs `model`
defined, not called. So "make sure the model code runs" is a statement about the JAX side.

#### Two things the live run taught us, neither predicted

1. **The parameter estimator reaches for the helpers too.** Its prompt shows it the model code, so it
   wrote `dudx_fn(...)` unprompted → `name 'dudx_fn' is not defined` → silent fallback to default
   params on 2 of 4 programs. Fixed by injecting `auxiliary` in `compile_param_est` and giving the
   helpers an `axis` argument: the model's `u` is 1-D over sensors (`axis=-1`), the estimator's
   `data['x']` is `(n_blocks, n_sensors, block_len)` so it must pass `axis=1`. The prompt says so
   explicitly. Second run: 4/4 estimators called the helpers with `axis=1`, no failures, no infs.
2. **The JAX translator redefines the helpers regardless of being told not to** (4/4 programs,
   `gemini-2.5-flash-lite`). Verbatim copies so far, but not guaranteed. Mitigated by ordering:
   helpers go **last** in the concatenation, so the project's vetted version shadows any LLM copy.
   Costs a few tokens per translation; left as is.

The journal's `dudx_fn` snippet had its **sign flipped** relative to the standard central difference
and to the oracle's convention (`ground_truth_model_o2_ab2.py:72`, `roll(u,-1) - roll(u,1) ~ +2 u_x`).
Corrected in the file — parameters absorb a sign, but reading `a` off a fitted model is the whole
point here.
